# Quarantined trusted-agent bootstrap

The Rust Docker driver has separate guarded creation and trusted-agent startup entry points. The subsequent [protected quarantine binding](protected-network-binding.md) composes source, DNS and destination protection while preserving Starting. A created container, a responding supervisor and a provider endpoint are not workload Ready. Production live orchestration, lease scheduling, policy updates, restart recovery and capability publication remain required. NetworkPolicy and SecretInjection stay unadvertised; the current production worker collects owned-network journals rather than publishing them as live workloads.

The ordinary none-network path now uses private `prepare_runtime` and `start_prepared` steps. Its configured image override, environment clearing, disabled image health checks, trusted read-only agent bundle, resource limits, namespaces and cleanup remain part of the same production path. An existing container with an owned-network plan cannot be adopted by the none-network create path.

`WorkloadNetworkPlan` combines the immutable native checkpoint with the exact provider network ID. It preserves installation/sandbox/generation/profile, original provisioning token, positive bridge index and absolute user expiry. The controller process UUID and image pin stay in the separate process plan so a later process replacement cannot silently change network identity. The caller must persist the creation intent and network plan before dispatching creation.

`DockerDriver::prepare_quarantined` validates the sandbox request against the actually probed profile and matches its identity, resource limits and deadline. It requires an actual enforcement session with the same frozen native plan and an unexpired dispatch deadline. It performs a full owned-network lookup and requires the exact physical ID and no attached endpoint. It inspects the actual controller, requires installed, certain inet and Ethernet protection, then writes a fresh quarantine through that private session and requires the correlated kernel readback. A cached observation or a caller-created receipt cannot substitute for this exchange. Collection-purpose sessions cannot authorize bootstrap.

Only then does the driver create the container on that physical network ID and attach the immutable plan label. It starts no process. A matching Created container can be recovered by the original create path; a different or missing plan cannot authorize adoption. The fixture commits the observed runtime handle to the file database with state Starting before it requests startup.

`start_quarantined` requires the original plan and an actual Created container. It checks the exact runtime/network, fixed mounted agent entrypoint, empty image command, disabled health checks, supervisor UID, capability set, no-new-privileges, private IPC, absence of host binds/devices and the single read-only agent volume. It again requires an empty matching network and a newly acknowledged quarantine before calling start. It waits for the trusted agent ping and then cross-checks the single attachment in both container and network inspections: physical container ID, endpoint ID, MAC, IPv4/IPv6 addresses, prefixes and gateways. Another start request against a running container is refused. An endpoint-readback failure after start removes the exact owned container and requires confirmed removal.

The endpoint observation is Docker metadata, not a native host-port/source guard, DNS binding, destination guard or lease receipt. Bootstrap publishes no user execution or successful create operation. The existing production recovery worker can remove either an unstarted Created runtime or the quarantined supervisor, settle the old controller, remove the empty bridge and collect owned filter tables before confirming sandbox cleanup.

The driver now adds a separate [native source-binding entry point](native-source-binding.md) after endpoint observation. The full contract binds provider addresses to the unique actual host port and independently audits the owned source floor. The new composed source path still requires hosted acceptance. Commit 920ad28's runc full/prepared-exit cases passed; its runsc startup and collection completed but the late creation-event assertion failed. The current contract captures startup events before worker probes and saves them before retaining the same exact count assertions.

`tests/guarded_bootstrap_contract.py` defines three actual backend modes. `full` starts the trusted supervisor under inet/Ethernet quarantine and checks both endpoint views, immutable placement, duplicate-start and none-network refusal. `prepared-exit` observes actual exit 79 after the runtime handle is committed and before any start request; independent inspection must still show Created with PID zero. Both then use the production worker and independent native readbacks to prove collection. Bounded Docker events must contain exactly one target runtime creation and respectively one or zero starts. The runc and gVisor network jobs require both modes.

`unavailable` requires an independently observed unsupported bridge-family kernel primitive. It then proves that the real driver refuses an inet-only floor before runtime creation and that the worker collects the remaining owned resources. It is prerequisite/refusal coverage and does not establish successful guarded startup. The local Docker Desktop kernel requires this mode; successful full/prepared-exit acceptance remains a separate hosted gate.

Three portable groups mutate synthetic inspections to exercise plan/none-network isolation, image-hook/host-authority admission and agreement of both dual-stack endpoint views. The native identity input comes from the existing controller fixture; the workload and peer records are synthetic. These tests do not establish actual startup or packet enforcement.

Initial local bootstrap attempts exposed a Windows debug stack overflow while a complete driver probe was polled inside the controller contract. Stage records located it after connection and before profile completion. Outer Future boxing alone did not resolve it. The fixture now joins an owned Tokio probe task, giving that probe the runtime task boundary used by reconciliation, and retains Future-size/stage observations. It does not raise process stack limits or omit the actual probe. Every failed attempt retains its raw failure and Complete scoped recovery; they are not counted as bootstrap passes.
