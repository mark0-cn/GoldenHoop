# Code context implementation and remaining work

The Rust sandbox agent, SQLite store, worker, public API, Rust/Python SDKs and CLI now implement Python kernel contexts. Capability advertisement requires an explicit optional driver probe configured with `--kernel-probe-image <cached-image>` or `GOLDENHOOP_KERNEL_PROBE_IMAGE`. The default worker leaves CodeContexts disabled. Isolated child sandboxes remain the next M2 increment. Existing language kernels are workload dependencies; orchestration stays in Rust. M2 is not complete.

The initial goldenhoop-jupyter crate implements bounded request framing and JSON-frame HMAC verification. Three portable tests cover an independently computed Python-stdlib signature vector, exact-byte verification, unsigned/tampered/wrong-key refusal, bounds and the protocol's unsigned routing/buffer scope.

A Linux-only experimental Rust peer now connects over IPC to an actual IPyKernel workload. The [initial local runc experiment](evidence/m2-kernel-ipc-runc-windows-docker.json) used zeromq 0.7 and observed authenticated kernel-info plus matching output-idle readiness, two snippets retaining state and returning 42, and a third snippet reporting the expected ValueError. Completion requires both the matching execute reply and output idle. Shutdown observed process exit 0 and private-file absence; the harness confirmed container and fixture-image removal. The workload used UID 1000, no network, a read-only root, dropped capabilities and bounded cgroup resources. The actual kernel reported Jupyter protocol 5.3. [Actual gVisor evidence](evidence/ci-45361158783/agent-runsc/kernel-runsc.json) now confirms that initial interoperability experiment on runsc too. This experiment is not the production agent context lifecycle, scoped UID collection, durable execution or public API.

## Execution boundary

A context owns one long-lived Jupyter-compatible kernel inside its source sandbox. The Rust agent owns startup, authenticated transport, queues, deadlines, observations and cleanup. The worker uses typed private agent requests and persists observations; it does not connect to workload-selected URLs. Kernel dependencies belong to the workload image. The minimal-image test verifies missing dependencies fail and collect without changing runtime or interpreter. A positive administrator fixture probe does not imply all workload images contain a compatible kernel.

Contexts retain interpreter state across snippets. They share the source workspace and its CPU/memory/task limits. They provide separate interpreter namespaces; isolated child sandboxes remain the separate M2 feature for a stronger execution boundary.

Normal commands/shells use UID 1000 and serialize because cleanup collects that UID's descendants. Kernels now use four agent-assigned UIDs (20000-20003) with shared workspace GID 1000, so collecting one context does not collect another context or a normal command. Callers cannot select a UID. Launches clear inherited environment, drop supplementary groups/capabilities and preserve no-new-privileges. Uploaded workspace files use mode 0660 and directories 02770 to allow group access. These identities scope process cleanup; contexts still share the sandbox filesystem and cgroup budget and are not isolated child sandboxes.

Slots remain reserved until actual live-UID descendant collection, child wait and private-directory removal are confirmed. Enumeration, status-read and signal errors cannot establish cleanup; disappeared processes are handled explicitly. Failed collection reports Unknown and retains the slot; the worker escalates it to whole-sandbox removal. The agent and host cap live contexts at four, total context history at 16, queued runs per context at eight, runs per context at 64 and total code-run history at 128. A code request is at most 64 KiB, with a 1-3600-second deadline and at most 16 MiB of serialized output events.

## Private kernel transport

The Rust Jupyter adapter uses the bounded Rust IPC transport described below. Kernel sockets use generated Unix paths in a private per-context directory. A root-owned mode-0711 parent under the sandbox's /tmp allows traversal but prevents workloads from listing or renaming context directories; each child starts at mode 0700 and is owned by its kernel UID. The actual kernel fixture adds a sticky bit (01700), retaining zero access for group/other users. Connection files are mode 0600 and contain only a fresh guest-local HMAC key. The existing private agent socket directory keeps its 0700/0600 boundary.

The adapter accepts only its generated IPC paths, fixed channel assignments and hmac-sha256. It verifies signatures over the original serialized JSON frames before parsing, correlates parent request IDs and tracks the kernel session epoch. Frame counts, bytes, JSON and output spools are bounded. Unknown optional protocol messages cannot establish readiness or completion. No host API/provider credential enters the kernel image, environment, connection file or output.

Startup must observe an authenticated kernel-info reply and usable output subscription. A kernel launch or connection-file write alone is insufficient. The actual implementation must handle subscription readiness without assuming a sleep proves delivery. Protocol-version negotiation must support the selected real fixture and reject incompatible versions explicitly.

Startup diagnostics retain at most 2 KiB of guest stderr and an observed child exit in a reason capped at 4 KiB. The reader continues draining after readiness while discarding capture, so raw fd-2 writes cannot block on an unread pipe or create an unbounded spool. Context collection stops and joins the reader. This is workload-provided diagnostic text, not a host-runtime verdict.

The [Jupyter messaging specification](https://jupyter-client.readthedocs.io/en/stable/messaging.html) defines the channel/framing/authentication contract. [IPyKernel connection documentation](https://ipykernel.readthedocs.io/en/stable/api/ipykernel.html) describes kernel connection files. The linked specifications support the design; actual runtime observations support the narrower experiment described above.

Review of zeromq 0.7's installed source found that its receive-buffer setting tunes chunk sizes rather than bounding declared message sizes. It also reconnects automatically. The reusable Linux `goldenhoop_jupyter::ipc` transport therefore implements the required single-peer subset of [ZMTP 3.0](https://rfc.zeromq.org/spec/23/) over Tokio Unix streams. It accepts generated IPC paths only, verifies peer UID and compatible READY socket type, and bounds each data frame to 2 MiB, each multipart payload to 16 MiB/64 frames and each command to 16 KiB before reserving a declared body. It has no TCP support, background receive queue, reconnection or resend. NULL framing is not authentication; Jupyter JSON HMAC verification remains required. These are payload bounds rather than an exact resident-memory quota; allocator capacity and decoded JSON add overhead within the sandbox cgroup budget.

An interrupted receive preserves decoder state. An interrupted or failed send closes further writes because delivery is ambiguous. Errors, partial messages and EOF require caller-controlled context collection. Five Linux regressions cover oversized declared lengths without allocation growth, too many/unfinished multipart frames, interrupted receive/resume, partial EOF, duplicate/truncated READY metadata, interrupted-send replay refusal, wrong peer UID and a bound-but-not-listening startup socket. Initial connection attempts for ENOENT/ECONNREFUSED wait at most two seconds before any protocol bytes are sent; this does not retry handshake/data failures or reconnect an established peer. A pathname alone does not establish listening readiness: [connect(2)](https://man7.org/linux/man-pages/man2/connect.2.html) documents refusal when no listener is available. The [bounded-transport runc experiment](evidence/m2-kernel-bounded-ipc-runc-windows-docker.json) and [actual gVisor experiment](evidence/ci-45362403663/agent-runsc/kernel-runsc.json) exercise the earlier real state/result/error/shutdown loop using this Rust transport. The [current gVisor kernel loop](evidence/ci-45389519170/agent-runsc/kernel-runsc.json) and optional driver probe also pass after the isolated network initialization correction described in [the driver contract](docker.md). The previous external ZeroMQ crate dependency is removed.

The reusable conversation layer accepts Jupyter 5.0-5.5, pins the authenticated kernel session epoch, correlates request IDs and channel roles, and refuses unsigned binary-buffer extensions. Readiness requires a matching shell kernel-info reply and output-channel idle; only kernel-info is safe to retry. The kernel's HMAC key is available to that kernel, so authenticated interpreter claims remain kernel claims rather than independent correctness proofs.

## Results and lifetimes

Code-run results are separate domain types from OS command executions. A kernel-reported successful reply is an interpreter observation, not process exit, malicious-code detection or independent correctness verification. A normal run completes only after matching authenticated execute-reply and output-idle observations. The kernel process remains alive and its resource cleanup remains a context-lifetime concern.

Private context events use an acknowledged, bounded in-memory context-wide cursor and optional originating run ID. The worker persists source hashes, acknowledgement, public event cursors and results atomically. Public SSE reads bound count and bytes, preserve cursor identity and hold a connection permit for the response body lifetime. A run retains its acceptance-time public cursor as `events_after`, including create-key replay. Late/background output is marked separately and does not mutate an already completed run result. A run's collected output ends at its observed idle cursor; subsequent output remains visible through context events with parent provenance and a separate 1-MiB context background budget. Output limits charge serialized event data and discard whole events that exceed the remaining budget, with one truncation observation. Unknown/mismatched messages, stream EOF and transport errors cannot synthesize success.

Cancellation and deadline expiry terminate the whole context and collect its UID's descendants, including setsid children. This discards that interpreter's state and is visible in the result. Queued undispatched runs become Cancelled only after cleanup. A kernel-reported exception can leave the context Ready; a crash, changed kernel epoch or invalid transport closes it with the affected run Unknown. Desired close is serialized with result publication and cannot be undone by late readiness or replies. Other contexts and the source sandbox can continue only after confirmed scoped collection. Graceful interrupt without context collection is not implemented.

The private-agent suite covers actual retained state, stdout/stderr/rich results, expected exception, duplicate request IDs without duplicate file writes, late background output, independent/concurrent contexts, UID-1000 command coexistence, cancellation/timeout with setsid descendants, queued-run cancellation, crash/epoch change without relaunch, output and wire bounds, UID-pool reuse and startup-close races. A separate minimal-image test confirms missing kernel dependencies fail and collect without fallback. Initial harness failures assumed exactly 0700 and were corrected after observing 01700 with no group/other access; their failure and permission observations are retained. These eight context groups and the missing-kernel case now pass on actual [gVisor](evidence/ci-45366452173/agent-runsc/contexts-runsc.json) and [runc](evidence/ci-45366452173/agent-runc/contexts-runc.json), with container and fixture-image cleanup confirmed.

## Durable control and validation

Create/run IDs and bounded queues have private-agent memoization. Reusing an ID with different content conflicts; a completed/failed context or run is never relaunched under that ID. Schema 4 persists host create/run identity, close/cancel intent and dispatch-before-RPC markers. The worker inspects stable agent IDs after restart and never resends a missing previously dispatched context or run. A crash immediately after the marker but before delivery is conservative: absent native history requires whole-sandbox removal, because delivery and scoped UID continuity cannot be established. Pending runs dispatch in durable acceptance order. A typed native refusal before acceptance can become Rejected; a transport failure cannot. Rejected is distinct from a kernel-reported exception.

Successful deletion requires actual process and private-directory absence; unknown cleanup stays charged. Public completion of cancellation/timeout waits for collection even when its agent proposal arrives in an earlier event batch. Source acknowledgement and public event cursors are independent; public run completions precede the final Closed event. Unexpected runtime loss leaves dispatched code Unknown, while host TTL collection can confirm TimedOut. Undispatched code is Cancelled without execution. A collected parent with unfinished child records remains in the recovery work scan. [Store semantics and nine file-backed durability tests](store.md) describe this host boundary.

Close/cancel requests commit intent during worker downtime. New creates/runs require a fresh worker profile that explicitly supports CodeContexts. A paused source cannot service private RPC, so close intent remains pending until resume or whole-runtime removal; its original host TTL continues. The worker allows a five-second close grace period before escalating to whole-sandbox removal, with bounded RPC/destruction time in addition. Other active contexts and commands can be lost during escalation, so callers should use isolated child sandboxes when that stronger failure boundary is required.

The [initial six actual public-context groups on local runc](evidence/m2-context-public-initial-runc-windows-docker.json) pass retained state and run replay across actual API/worker restarts, independent namespaces and command coexistence, cancellation/timeout with escaped descendants, kernel exceptions/crash/epoch change/wire bounds, missing workload dependencies, actual runtime loss with undispatched code, missing dispatched context history, and paused expiration while the API is down. Context events and collection are checked through the public API. The [initial 22-case full API regression](evidence/m2-context-public-runc-windows-docker.json) also passes. Owned containers, bundle volumes, processes and temporary files are confirmed removed.

All four [actual context client loops on local runc](evidence/m2-context-clients-initial-runc-windows-docker.json) now pass retained state, replayed results without duplicate writes, rich output, kernel exceptions, event resume, queued-run cancellation, timeout collection and uncertain crash handling. Async Python also cancels an observer task and verifies the code continues exactly once. Collectors start from the accepted run's retained cursor, validate identity/sequence and require an explicit matching result. CLI kernel exceptions return 1, timeouts 124 and uncertain observations 125; these do not claim an OS kernel-process exit code. [Client usage](clients.md). Actual gVisor/S3 public context loops remain separate CI gates.

The [full 22-case local API/client regression](evidence/m2-context-api-clients-runc-windows-docker.json) passes with these new bindings and the corrected none-network setup. It includes prior command/file/session/PTY/artifact behavior alongside the public context groups and all four clients, and confirms cleanup of its owned containers, volumes, processes and temporary directory.

Required tests include two snippets sharing state, independent context namespaces, command/context coexistence, concurrent contexts, real stdout/stderr/results/errors, authenticated message and parent-ID refusal, bounded output, actual worker/API downtime, no duplicate snippet execution, kernel crash, timeout/cancel with setsid descendants, context deletion races, and source pause/expiry. All supported clients must execute a real loop. Actual runc and gVisor gates precede capability advertisement as verified. Fixture images, private connection files, containers, volumes and temporary directories must be collected on both successful and failed runs. Unsupported kernels and missing runtime evidence remain unverified.
