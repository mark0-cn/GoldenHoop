# Persistent control state

The SQLite store uses SQLx, WAL journaling, full synchronization and immediate write transactions. A stable installation UUID is initialized atomically and retained across restarts. Schema version 3 adds sessions and input controls to the artifact metadata and generic operation resource IDs introduced in version 2. Versions 1 and 2 upgrade transactionally while preserving identities and operations. Unsupported versions are refused. PostgreSQL and cluster migrations remain part of M5.

The API commits desired state and idempotent requests before the worker acts. Observations update actual state without overwriting a concurrent desired-state change or extending the original absolute deadline. A terminated state requires confirmed cleanup. Failed resources with unconfirmed cleanup remain charged to the installation quota.

The initial installation limits are 16 live sandboxes, 16 CPU equivalents, 32 GiB memory and 4096 PIDs in total, with at most a one-day TTL and 256 executions per sandbox. Profile limits may be stricter. Image metadata, argv and environment sizes are bounded before storage or execution.

Commands have stable UUIDs and persisted cancellation intent. Events, their acknowledgement cursor and the public execution result commit in one transaction. Event sequences must be contiguous and duplicate sequences must retain the same content. Each stream has at most one completion event. A terminal result requires a matching explicit completion event and confirmed process cleanup; Unknown does not satisfy completion. Terminal results and completed streams are immutable.

Worker metadata contains a private loopback endpoint and authentication token. It is not a public response type. A stale heartbeat cannot advertise a live worker. New database files use mode 0600 and newly created parent directories use mode 0700 on Unix; existing database files with group/other permissions are refused. On Windows, access follows the owning user's directory ACLs. Do not share the state directory with workloads.

The durability suite covers concurrent idempotency, failed transaction rollback, resource charging until confirmed cleanup, desired-state races, absolute expiration, completion/cursor atomicity, terminal immutability, cancellation preservation, stale heartbeat refusal and actual SQLite close/reopen. Temporary database files are removed after the suite, including assertion failure paths.

The public API, worker reconciliation loop, CLI and SDKs now use these primitives; see control.md and clients.md.

Artifact metadata reserves identity and idempotency before capture. Prepared content length/digest are immutable. Availability and operation completion commit atomically, and a concurrent deletion intent cannot be overwritten by a late upload observation. Completed deletion cannot be resurrected. Pending deletion/uploading states survive database close/reopen. The initial limit is 256 retained or uncollected artifacts; failed cleanup remains charged until absence is confirmed. The worker, public API, SDKs and CLI use these primitives.

A storage namespace fingerprint binds the database to its canonical local root or explicit S3 endpoint/bucket/region. It excludes credentials to allow rotation. Changing the namespace requires migration and otherwise fails closed. Actual late blob residue can reopen a failed/deleted artifact's cleanup as Unknown without changing its terminal business state or completed operation. It consumes quota until the worker reconfirms absence. Cleanup is a timestamped observation. See [artifact reconciliation](artifacts.md).

Sessions reuse durable execution identities, cancellation, event cursors and history quotas. Their specifications and ordered controls are additional tables. Session/command create keys have separate scopes. Control sequence/content jointly provide idempotency; gaps conflict and limits are 1024 controls, 64 KiB per write and 1 MiB total input per session. Input receipts distinguish pending, applied, rejected and unknown; settled observations are immutable. Publishing a terminal execution atomically marks any unconfirmed inputs Unknown. Applied means input delivery, not successful code execution. Session worker/public integration remains pending; [the contract](sessions.md) distinguishes that work from the tested persistence layer.
