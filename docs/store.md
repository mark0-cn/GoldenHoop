# Persistent control state

The SQLite store uses SQLx, WAL journaling, full synchronization and immediate write transactions. A stable installation UUID is initialized atomically and retained across restarts. Schema version 4 adds code-context/run metadata and separate source/public event cursors to sessions/input controls (version 3) and artifact metadata/generic operation IDs (version 2). Versions 1-3 upgrade transactionally while preserving identities and operations. Unsupported versions are refused. PostgreSQL and cluster migrations remain part of M5.

The API commits desired state and idempotent requests before the worker acts. Observations update actual state without overwriting a concurrent desired-state change or extending the original absolute deadline. A terminated state requires confirmed cleanup. Failed resources with unconfirmed cleanup remain charged to the installation quota.

The initial installation limits are 16 live sandboxes, 16 CPU equivalents, 32 GiB memory and 4096 PIDs in total, with at most a one-day TTL and 256 executions per sandbox. Profile limits may be stricter. Image metadata, argv and environment sizes are bounded before storage or execution.

Commands have stable UUIDs and persisted cancellation intent. Events, their acknowledgement cursor and the public execution result commit in one transaction. Event sequences must be contiguous and duplicate sequences must retain the same content. Each stream has at most one completion event. A terminal result requires a matching explicit completion event and confirmed process cleanup; Unknown does not satisfy completion. Terminal results and completed streams are immutable.

Worker metadata contains a private loopback endpoint and authentication token. It is not a public response type. A stale heartbeat cannot advertise a live worker. New database files use mode 0600 and newly created parent directories use mode 0700 on Unix; existing database files with group/other permissions are refused. On Windows, access follows the owning user's directory ACLs. Do not share the state directory with workloads.

The durability suite covers concurrent idempotency, failed transaction rollback, resource charging until confirmed cleanup, desired-state races, absolute expiration, completion/cursor atomicity, terminal immutability, cancellation preservation, stale heartbeat refusal and actual SQLite close/reopen. Temporary database files are removed after the suite, including assertion failure paths.

The public API, worker reconciliation loop, CLI and SDKs now use these primitives; see control.md and clients.md.

Artifact metadata reserves identity and idempotency before capture. Prepared content length/digest are immutable. Availability and operation completion commit atomically, and a concurrent deletion intent cannot be overwritten by a late upload observation. Completed deletion cannot be resurrected. Pending deletion/uploading states survive database close/reopen. The initial limit is 256 retained or uncollected artifacts; failed cleanup remains charged until absence is confirmed. The worker, public API, SDKs and CLI use these primitives.

A storage namespace fingerprint binds the database to its canonical local root or explicit S3 endpoint/bucket/region. It excludes credentials to allow rotation. Changing the namespace requires migration and otherwise fails closed. Actual late blob residue can reopen a failed/deleted artifact's cleanup as Unknown without changing its terminal business state or completed operation. It consumes quota until the worker reconfirms absence. Cleanup is a timestamped observation. See [artifact reconciliation](artifacts.md).

Sessions reuse durable execution identities, cancellation, event cursors and history quotas. Their specifications and ordered controls are additional tables. Session/command create keys have separate scopes. Control sequence/content jointly provide idempotency; gaps conflict and limits are 1024 controls, 64 KiB per write and 1 MiB total input per session. Input receipts distinguish pending, applied, rejected and unknown; settled observations are immutable. Publishing a terminal execution atomically marks any unconfirmed inputs Unknown. Applied means input delivery, not successful code execution. The public API, WebSocket and worker use these primitives; see [the session contract](sessions.md).

Code-context primitives persist create/run identity and content, close/cancel intent, dispatch-before-RPC markers, history/queue quotas and immutable event observations. Open/closed desire is separate from observed state and cleanup. A dispatch method returns true once; a restart cannot interpret an already-dispatched but missing ID as permission to resend code. Native-agent memoization supplies the other half of recovery. The worker, public routes and clients are not integrated with these new primitives yet; CodeContexts remains unadvertised.

Source sequence/content hashes, source acknowledgement, public events and resulting records commit atomically. Public context event cursors are independent of agent acknowledgement cursors. Kernel success/error can publish only from a matching explicit run-completion observation with valid timestamps and status. Cancellation, timeout and Unknown proposals await actual context collection. After a close intent, a late kernel result is retained as a diagnostic and becomes Cancelled only after collection. Public run completions precede the final Closed event. Unknown cleanup has no final Closed event, leaves uncollected work Unknown, and stays charged until the worker confirms runtime absence. The absence reconciler cannot synthesize kernel success.

Per-sandbox code limits match the native agent: four uncollected context identities, 16 contexts in history, eight queued runs per context, 64 runs per context and 128 code runs in total. Run output is checked against its accepted serialized-event budget; late/background output has a separate 1-MiB context budget and cannot mutate a completed run. Gaps, altered replay, wrong run IDs, output before run start and output beyond budget fail the transaction. Host quota enforcement does not provide a separate context cgroup or filesystem isolation boundary.

Six file-backed SQLite tests cover concurrent identity reservation, immutable completion with late output, close/result ordering, deferred cancellation and source/public cursor separation, unknown cleanup charging, transactional event/budget rollback, queue reservation rollback, schema-3 migration preserving session/artifact identities, and actual close/reopen preserving ambiguous dispatch and cancellation. They use synthetic runtime observations and do not establish a public code-context execution loop. Test databases are removed on success and assertion failure.
